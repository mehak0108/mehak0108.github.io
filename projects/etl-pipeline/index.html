Architected a hybrid batch and event-driven ETL pipeline on Apache Airflow and Kafka, serving 10+ retail clients with completely different source systems — built around the principle that a backend pipeline failure should never block a customer at checkout.

Problem

Every retailer onboarding to Mishipay brought a different source system: a UAE supermarket sending nightly flat files from SAP, a Danish retailer expecting real-time REST posting, a US grocery chain whose API wasn't ready, a Dubai duty-free operator sending 200,000+ SKUs with RFID tags and duty-free allowance rules in custom fields. Off-the-shelf ETL tools like Fivetran handle standard schemas — they don't handle a SKU that's in column 3 of one client's CSV and a field called "item_reference" in another's JSON.

The real design question was how to make it reliable enough to power live retail checkout, flexible enough for any source format, and maintainable enough that onboarding clients didn't mean rebuilding from scratch.

Solution

I structured the architecture around three answers: extraction logic is fully client-specific (one Python parsing script per client is the only place client code lives), transformation and load are shared and identical regardless of source, and data latency requirements vary by type — so the pipeline runs two tracks. Batch (Airflow, scheduled) handles product catalogs and promotions, where overnight latency is acceptable. Real-time (Kafka + Azure Serverless) handles order transactions and loyalty events, where a delay of even minutes causes real problems.

Before integrating any new client, I established a data contract with their IT team, specifying exact fields, types, nullability, and delivery method. This caught the kind of mismatch that would otherwise surface as a production incident; for DDF's 200,000-SKU catalog, a single undocumented null in the tax code field would have caused thousands of checkout failures on go-live day.

The most consequential design decision was failure handling, treated as a product specification rather than an engineering afterthought. I defined the acceptable degradation for each failure mode with the client before build: if product_sync fails overnight, the kiosk serves yesterday's catalog rather than failing; if order_export fails, transactions still complete on the kiosk and queue locally for idempotent re-export. The principle driving all of it: checkout is the revenue-generating moment, and no backend pipeline failure should ever be the reason a customer can't complete a purchase.

Outcome

The pipeline now powers 10+ retail clients on a shared transformation and load layer, with each client's quirks isolated to a single parsing script. Load testing validated capacity to 4.4M transactions for Flying Tiger Copenhagen alone, which posted $46.8M in transaction value via the rebuilt event-driven pipeline after the original synchronous integration became a bottleneck. Dubai Duty Free's 200,000+ SKU catalog syncs nightly with zero manual intervention, contributing to a 35% average basket increase. Event Network's migration from file-based to real-time API posting drove a 7.6% footfall capture lift against a 0.8% expectation.
