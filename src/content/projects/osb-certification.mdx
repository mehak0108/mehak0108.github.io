## Executive Summary

As service providers began onboarding to cloud platform, a critical gap emerged: there was no enforced standard for how each provider implemented the Open Service Broker (OSB) API, the protocol Cloud Foundry uses to manage every service lifecycle. Without a contract, the platform had no reliable way to interpret provider responses, handle errors consistently, or demonstrate pre-onboarding validation to internal audit teams.

I designed and built an asynchronous certification suite that every service provider must pass before their service is listed on the marketplace. The suite tests the full OSB lifecycle, create, bind, unbind, delete, including error handling and edge cases, and produces a structured pass/fail report with visual output. It functions as the marketplace's quality gate: providers self-serve their way to compliance, and the platform team gets a documented certification trail for every listed service.

## Background & Context

Gaia Cloud Platform is JP Morgan's internal service marketplace, allowing developer teams to discover and provision infrastructure services across Cloud Foundry and Kubernetes. Cloud Foundry communicates with every listed service through the Open Service Broker API, a standard protocol covering the complete service lifecycle: create instance, bind to app, unbind, and delete.

  <figcaption>The Open Service Broker API: a standard contract between Cloud Foundry and every service it provisions</figcaption>

The OSB spec defines the contract in theory. In practice, each service provider builds their own OSB implementation independently. As the number of providers onboarding to Gaia Portal grew, it became clear that the platform was operating on a faulty assumption: that all OSB implementations were equivalent. They were not.

**Key Stakeholders**

- **Service Providers** — teams building and listing infrastructure services on Gaia Portal
- **Platform Team (Cloud Foundry / GTI)** — consuming OSB APIs at runtime on every provisioning operation
- **Security & Compliance** — requiring documented pre-onboarding validation for all services handling financial data
- **Developer Consumers** — downstream teams whose provisioning reliability depends on well-behaved OSB implementations

Reference: [openservicebrokerapi.org](https://www.openservicebrokerapi.org/)

## Problem Statement

The OSB spec defines the interface, but does not enforce it. Service providers could implement it however they chose, and Cloud Foundry had no mechanism to handle that variation without custom-coding logic for each provider, which does not scale across an enterprise platform.

**Three Concrete Risks**

- **Unpredictable response formats** — A provider returning a non-standard error code or malformed response body causes the platform to fail silently or throw unhandled exceptions. Developers get no actionable error; the platform team gets an escalation.
- **Unhandled edge cases** — Without validating timeout behavior, retry handling, or delete/unbind correctness, services could leave orphaned bindings after termination, resources allocated but never cleaned up, creating data and cost exposure.
- **Compliance gap** — At JP Morgan, services on the platform have the potential to access or process sensitive financial data. Onboarding an unvalidated service creates an audit gap: no documented evidence that the service behaved correctly across all lifecycle operations before going live.

**Problem Framing**

- **User (Service Provider):** "I've built my OSB implementation. How do I list my service on the marketplace?"
- **Current experience:** Submit details, wait for manual review, get ad-hoc feedback from the platform team, iterate without visibility into what specifically failed.
- **Desired experience:** Submit details, get a link to an automated report, see exactly which tests failed and why, fix and resubmit, no platform team involvement needed.
- **Business impact:** Inconsistent OSB behavior causes runtime provisioning failures for consuming teams, creates compliance exposure, and overloads the platform team with reactive debugging.

## Solution — Async OSB Certification Suite

The certification suite is an asynchronous test harness integrated into the Gaia Portal provider onboarding flow. It hits the service provider's OSB API across all lifecycle operations, validates responses against the OSB spec and JP Morgan's enterprise standards, and generates a structured pass/fail report. A service cannot be listed on the marketplace until it passes.

**Key Design Decisions**

- **Async execution** — Tests run in the background without blocking the UI. The provider receives a confirmation with a link to a live report, which updates as tests complete.
- **Full lifecycle coverage** — Tests span all four OSB operations (create, bind, unbind, delete), not just the happy path, mirroring what CF will do at runtime.
- **Edge case validation** — Beyond standard flows, tests cover non-standard error codes, malformed error messages, timeout handling, and retry behavior.
- **Self-serve report** — Pass/fail status per test with structured failure descriptions lets providers debug without contacting the platform team.
- **Pie chart summary** — Visual pass/fail distribution gives an at-a-glance health signal before providers dive into individual results.

## Compliance Angle

At JP Morgan, this was not purely an engineering quality control decision. Services listed on cloud marketplace provision and manage resources that may access or process sensitive financial data. The absence of a pre-onboarding validation process created regulatory and audit exposure across three dimensions:

<table>
<thead>
<tr><th>Risk</th><th>Exposure Without Suite</th><th>How the Suite Mitigates It</th></tr>
</thead>
<tbody>
<tr><td>No audit trail</td><td>No documented evidence that a service was tested before going live — creates gap for internal audit and regulatory review</td><td>Every listed service has a timestamped, structured certification report on record showing which tests passed, failed, and when the service was cleared</td></tr>
<tr><td>Resource leakage risk</td><td>Unvalidated unbind/delete flows could leave data resources allocated after service termination, a data governance and cost control issue</td><td>The suite explicitly tests delete and unbind correctness, including non-existent instance handling, before the service is permitted on the platform</td></tr>
<tr><td>Non-standard error handling</td><td>Unpredictable error responses from provider OSBs can mask failures in regulated provisioning workflows, creating reporting blind spots</td><td>Test cases cover error code format, error message structure, and timeout behavior, enforcing a consistent, interpretable error contract across all providers</td></tr>
</tbody>
</table>

The certification suite shifted the compliance posture from reactive (discovering non-compliant behavior after listing) to proactive (enforcing a documented gate before any service reaches the marketplace). Every service on cloud marketplace has earned its listing.
