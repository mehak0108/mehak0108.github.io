## The Problem: Why a Custom Pipeline

Every retailer that onboards to Mishipay brings its own source systems, data formats, and operational expectations. A UAE premium supermarket sends its product catalog as a nightly flat file from SAP. A Danish variety retailer expects real-time transaction posting via REST API. A US grocery chain's API wasn't ready at all, requiring a file-based integration as an interim. A Dubai duty-free operator sends 200,000+ SKUs with RFID tag IDs, LAG eligibility flags, and duty-free allowance rules embedded in custom fields.

Off-the-shelf ETL tools like Fivetran or Stitch handle standard schemas well. They don't handle the case where a retailer sends a CSV in which the SKU is in column 3 for one client and in a field called "item_reference" in a JSON response for another. The parsing logic is client-specific by necessity, it lives in the ETL layer, not in the core platform.

The real design question was: how do you build a pipeline that's reliable enough to power live retail checkout, flexible enough to handle any source format, and maintainable enough that a new client doesn't require rebuilding from scratch?

Both tracks share the same transformation layer, the difference is in how data enters and how quickly it must be delivered.

Once data passes through the parsing script, it conforms to Mishipay's canonical schema and is handled identically regardless of which client it came from.

A tax code in one retailer's system maps to a different code in another's. A promotions rule that Grandiose calls a "promotion_group" is what DDF calls a "discount_type."

### The Data Contract

Before writing any ETL parsing script, Mishipay agrees a data contract with the retailer's IT team. The contract specifies the exact fields that will be provided, their data types, which fields are nullable, the update frequency, and the delivery mechanism. This is a product artefact, it protects both sides from scope creep and gives the integration team a clear target.

Investing in a formal data contract before development starts prevents the most common source of mid-project rework: discovering that a required field is missing, has a different format than expected, or isn't populated for a subset of records. For DDF's 200,000-SKU catalog, a single undocumented null field in the tax code column would have caused thousands of checkout failures on go-live day.

When a retailer changes their source file format without notice, which happens, the ETL script's validation layer catches the change at extraction time and alerts the team before corrupted data reaches the shared database. This is preferable to discovering the issue when a kiosk fails to find a product at checkout.

## Airflow DAG Architecture

### Why Airflow over Cron Jobs

Simple cron jobs handle scheduling, but they provide no visibility into task dependencies, no built-in retry logic, no alerting on failure, and no way to reprocess historical data. Apache Airflow gives the pipeline operator a live view of every run, every task state, and every failure. When a product sync fails at the transform stage, Airflow makes it immediately clear which task failed, what error it returned, and whether the retry policy has been exhausted, without requiring log inspection.

- **Task dependencies:** Airflow enforces that the load task only runs if validation passed. A failed validation cannot silently allow corrupt data to load.
- **Idempotency:** every load task is designed to produce the same result if run twice, critical for retry logic. Running `product_sync` twice on the same data doesn't create duplicate SKUs.
- **Backfill capability:** if a sync was missed (due to a source system outage), the pipeline can be triggered manually for a specific date range and will reprocess correctly.
- **Observability:** every task run, its duration, its exit state, and its output are recorded. This made it possible to identify the FTC bottleneck, a specific task was taking 40 minutes for 80K transactions, exposing the architectural limit before it hit 4.4M in production.

## Real-Time vs. Batch: The Design Decision

The most consequential pipeline design decision is about acceptable data latency. Making everything real-time would reduce latency to near-zero for all data types, but at the cost of significantly higher operational complexity, more failure modes, and higher infrastructure cost. Making everything batch would eliminate complexity, but mean a promotion change takes until the next morning to take effect. The right answer is a deliberate hybrid based on the business impact of stale data for each data type.

<table>
<thead>
<tr><th>Data Type</th><th>Acceptable Latency</th><th>Chosen Approach</th><th>Business Reason</th></tr>
</thead>
<tbody>
<tr><td>Product catalog</td><td>Up to 24 hours</td><td>Batch — 02:00 UTC nightly</td><td>Products rarely change intraday. Price or name updates can wait until overnight sync without customer impact.</td></tr>
<tr><td>Promotions rules</td><td>Before store opens</td><td>Batch — 04:00 UTC + on-demand trigger</td><td>Must be active when the first transaction runs. An on-demand trigger handles urgent same-day promotion changes.</td></tr>
<tr><td>Order transactions</td><td>Seconds</td><td>Real-time — Kafka event-driven</td><td>Retailers need transaction data for inventory and financial systems immediately. A 15-minute lag causes operational issues.</td></tr>
<tr><td>Loyalty earn</td><td>Seconds</td><td>Event-triggered post-payment</td><td>Customer's loyalty points must post before they leave the store. A delayed earn is a trust failure.</td></tr>
<tr><td>Settlement</td><td>End of day</td><td>Batch — 23:30 UTC EOD</td><td>Payment reconciliation follows a natural EOD cycle. Intraday settlement provides no additional value.</td></tr>
</tbody>
</table>

The 24-hour latency window for product data was an explicit product decision agreed with each client. It's a trade-off: nightly batch is simpler, cheaper, and has fewer failure modes than continuous sync. Agreeing this boundary with the client before build prevents the expectation mismatch that turns into a support escalation at 09:00 when a price change from 08:30 hasn't yet propagated.

## Transformation Logic

### Product Data Normalisation

The transformation layer converts each retailer's native data format into Mishipay's canonical product schema. The same product fields exist in every retailer's system, but they arrive under different names, in different types, and with different encodings. The transform step handles this without any client-specific code in the shared transformation module, the client-specific mapping lives in the ETL parsing script that precedes it.

### Promotions Rule Parsing

Promotions data is the most complex transformation in the pipeline because each retailer expresses the same rule concepts in structurally different ways. Grandiose sends its mix and match rules as a flat file with a `promotion_group_id` and a comma-separated list of `qualifying_skus`. DDF sends its discount day rules as a JSON object with a `discount_type` field and an `item_category` code. Both need to be transformed into Mishipay's canonical promotion rule format before they can be loaded into the shared database and evaluated by the core promotions engine.

- The promotion schema defines: `rule_type` (mix_and_match, combo, staff_discount, custom), `qualifying_items` (array of SKUs or category codes), `discount_value`, `discount_type` (percentage or fixed), and `validity_window`.
- The parsing script for each client translates their native format into this canonical structure. Once loaded into the shared database, the core promotions engine evaluates all rules identically regardless of which client they came from.
- Validation at this stage is critical: a promotion rule with a missing `qualifying_items` array will be rejected by the validator and won't load, rather than loading silently and failing to apply at checkout.

Defining a promotion schema before onboarding the second client was the decision that made multi-client promotion management tractable. Without it, each client's promotions would be evaluated by client-specific logic in the core engine, a maintenance debt that compounds with every new client. The schema was designed to be expressive enough to represent every promotion type any client had requested up to that point, with an extension mechanism for future types.

## Failure Handling — When the Pipeline Breaks Before a Store Opens

When `product_sync` fails at 02:30, the question "what does the checkout experience look like?" is agreed with the client before building. Here are the four primary failure scenarios and the agreed response for each.

<table>
<thead>
<tr><th>Failure Scenario</th><th>Immediate Effect</th><th>Agreed Response</th><th>Alert Level</th></tr>
</thead>
<tbody>
<tr><td>product_sync fails overnight (retries exhausted)</td><td>Kiosk serves yesterday's product catalog. Price or product availability changes since last successful sync aren't reflected.</td><td>Kiosk continues operating on cached data. Acceptable up to 24 hours, most catalog changes are minor. Alert sent to engineering and customer success after retry 1. Manual re-trigger available.</td><td>Medium — alert after retry 1</td></tr>
<tr><td>promotions_sync fails before store opens</td><td>Yesterday's promotion rules are active. A new promotion scheduled to start today doesn't apply at checkout.</td><td>Checkout continues with previous day's promotions. Alert sent immediately. Customer success notified to check with retailer. On-demand re-trigger available for urgent same-day fixes.</td><td>High — alert immediately</td></tr>
<tr><td>order_export fails (Kafka consumer or DAG failure)</td><td>Transaction records aren't posted to the retailer's ERP. A gap forms in their financial and inventory data.</td><td>Transactions complete on the kiosk, checkout is never blocked by an outbound export failure. Orders are queued locally and re-exported when connectivity or the DAG restores. Re-export is idempotent, no duplicates.</td><td>Medium — alert after retry 2</td></tr>
<tr><td>settlement_sync fails (EOD batch)</td><td>End-of-day financial reconciliation between Mishipay and the payment gateway doesn't complete. Manual reconciliation is required.</td><td>Alert sent immediately to engineering, payments team, and customer success. A manual settlement export command is available. This is the only failure mode with a potential financial impact, zero tolerance for silent failure.</td><td>Critical — alert immediately</td></tr>
</tbody>
</table>

The decision that checkout should never be blocked by an outbound pipeline failure, `order_export`, `settlement_sync`, was the most important product call in failure handling design. The SCO kiosk is the revenue-generating moment. Any architecture where a backend pipeline failure stops a customer from completing a transaction is the wrong architecture. Separation of inbound data dependencies (product catalog must be fresh enough) from outbound reporting (can queue and retry) reflects this principle.
